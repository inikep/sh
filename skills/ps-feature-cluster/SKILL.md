# Percona Server: feature clustering report

## Purpose

Given a commit range `$BASE_BRANCH..$TIP_BRANCH`, produce two markdown deliverables:

1. **`features-report.md`** — per-commit catalogue of what each commit introduces: new server/plugin sysvars, new long options, new `SQLCOM_*`, new yacc tokens, new files (bucketed by area), new C/C++ macros and types, plus content-derived feature tags.
2. **`cluster-summary.md`** — a table grouping commits into feature clusters anchored on **seeds** (commits that introduce a feature), with **strong satellites** (commits whose combined affinity to the seed ≥ a threshold) and **weak satellites** (below the threshold but non-zero), plus per-cluster prose with the "why related" signal that fired, a separate inverse-diff replacement/revert candidate table, and a per-commit feature-impact table showing what each commit introduces, updates, removes/replaces, or is replaced by.

Cluster assignment uses a combined affinity graph. Phase 5 computes the base relatedness from four signals:

- `hunk_w` — line-overlap counts from the hunk-level dependency graph
- `file_w` — TF-IDF-weighted shared-file count (rare files matter more)
- `tok_w` — shared bug/patch/lp/mdev/cve/bp tokens from subject + body; leading bracketed subject markers such as `[feature_name]` are ignored
- `sym_w` — C/C++ symbol-level signals: co-defined macros/types, def-use across commits, shared `(file, function)` contexts

Phase 7 adds the fifth signal, inverse-diff replacement/revert evidence, into the clustering affinity. It compares exact normalized added/deleted lines across commit pairs and flags cases where a later commit deletes lines introduced by an earlier commit or re-adds lines removed by an earlier commit. Each candidate is annotated with DAG movability: `adjacent`, `move-member-up`, `move-carrier-down`, or `blocked`. The raw replacement table remains in the report as a review aid, but it is no longer merely advisory for clustering.

The skill is **read-only** — it never modifies the commit range or any branch. If you want to actually squash the clusters into a single-commit-per-feature branch, use `ps-squash-dag` (or its `squash_features.py` variant) afterwards.

## Inputs

| Variable                | Default                                  | Meaning                                                                                          |
| ----------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `$BASE_BRANCH`          | required                                 | Lower bound of source range (e.g. `mysql-5.6.26`).                                               |
| `$TIP_BRANCH`           | required                                 | Upper bound — the branch being analysed.                                                         |
| `$WORK_DIR`             | `/tmp/ps-feature-cluster-${TIP_BRANCH}`  | Where intermediate JSON/TSV + report files live.                                                 |
| `$SEEDS_FILE`           | `${WORK_DIR}/seeds.tsv`                  | Tab-separated `feature_name TAB seed_idx_1,seed_idx_2,...`. Generated by `seeds.py` if absent.   |
| `$MIN_AFFINITY`         | `4.0`                                    | Minimum affinity required for a satellite to join a cluster.                                     |
| `$STRONG_AFFINITY`      | `10.0`                                   | Affinity threshold above which a satellite is "strong" (else "weak").                            |
| `$MARGIN`               | `1.3`                                    | Winner's affinity must exceed runner-up by this margin (else commit is "ambiguous").             |
| `$REPLACEMENT_AFFINITY_SCALE` | `4.0`                              | Multiplier for inverse-diff replacement/revert evidence during cluster assignment.                |
| `$REPLACEMENT_AFFINITY_CAP`   | `24.0`                             | Maximum affinity contribution from one inverse-diff replacement/revert pair.                     |
| `$SEED_MERGE_AFFINITY`        | `20.0`                             | Minimum combined affinity for merging two seed features into one cluster.                         |
| `$SEED_MERGE_REPLACEMENT_MIN_SCORE` | `5`                         | Minimum inverse-diff score required for the conservative seed-feature merge pass.                 |
| `$SEED_MERGE_REQUIRE_MOVABLE` | `1`                                | If nonzero, seed-feature merges require replacement movability other than `blocked`.              |

## Hard rules

- **HR-1** — Skill is read-only. Never modifies branches, never cherry-picks. Output is two `.md` files plus intermediate JSON/TSV.
- **HR-2** — Seeds must be commit indices, not SHAs (so the file survives commit-rewrites of the range). If the user supplies SHAs, `seeds.py` resolves to current indices first.
- **HR-3** — Per-cluster total = seeds + strong + weak (no overlap; each non-seed commit is assigned to at most one cluster).
- **HR-4** — Markers (commits with no code), version bumps, and packaging-only commits are excluded from satellite assignment. They appear in the **Unassigned** section of the report.
- **HR-5** — Affinity is computed as **max** combined edge weight to any seed of the feature (max-link), not mean. This captures "anchor edge to feature" cleanly and lets a satellite join even when it has only one strong tie.

## Phases

Seven read-only phases. Phases 1–5 are deterministic; phase 6 is the seed-decision point (engineer can edit `seeds.tsv`); phase 7 writes the final reports.

### Phase 1 — Index commits (`scripts/index.py`)

For every SHA in `git rev-list --reverse $BASE_BRANCH..$TIP_BRANCH`:

- subject, body, files-touched. Phase 1 stores the raw subject as `raw_subj`, but strips leading bracketed feature-marker prefixes from `subj`; later phases treat markers as metadata rather than feature evidence.
- per-file hunk ranges from `git show -U0`: pre/post line ranges
- binary / new-file / deleted-file flags

Writes `$WORK_DIR/commits.json`.

### Phase 2 — Hunk-level dependency graph (`scripts/depgraph.py`)

Walk chronologically maintaining a blame frontier per path. For each commit's hunks: emit edges to all earlier commits whose lines this commit modifies; splice frontier accordingly.

Writes `$WORK_DIR/dep-edges.tsv` (one row per `(idx_A, idx_B, path, A_post_range, B_pre_range)`).

### Phase 3 — Symbol extraction (`scripts/symbols.py`)

For every commit, parse `git show -U0` and extract from `+`/`-` lines in C/C++ files (`.h/.c/.cc/.cxx/.cpp/.hh/.hpp/.hxx/.i/.ic`, excluding `mysql-test/` and `.h.pp` ABI fixtures):

- `added_defs` — identifiers DEFINED on `+` lines: `#define NAME`, `typedef … NAME;`, `struct/union/class/enum NAME`, function definitions (heuristic regex)
- `removed_defs` — same patterns on `-` lines
- `refs` — all identifiers ≥ 4 chars on `+` lines that aren't in `added_defs` (i.e. uses, not introductions)
- `contexts` — set of `(path, hunk_function_label)` pairs from `@@ … @@ <ctx>` headers

For every commit pair, compute symbol-level edge weight contributions:

| Component       | Meaning                                                | Weight |
| --------------- | ------------------------------------------------------ | ------ |
| `co_def`        | Both commits define the same symbol                    | ×10    |
| `def_use`       | A defines X, B references X (or vice versa)            | ×2     |
| `co_remove`     | Both commits remove the same symbol                    | ×4     |
| `shared_ctx`    | Both touch the same `(file, function)` pair            | ×3     |

Writes `$WORK_DIR/symbols.json` and `$WORK_DIR/symbol-edges.tsv`.

### Phase 4 — Feature extraction (`scripts/features.py`)

For each commit, scan `+` lines and extract:

- New files added (`{new: true}`), bucketed by area: MTR test, header, InnoDB, sql/, plugin, scripts, other.
- **Plugin sysvars** via `MYSQL_(?:SYSVAR|THDVAR)_[A-Z]+\(\s*<name>,`.
- **Server sysvars** via `static\s+Sys_var_\S+\s+Sys_\S+\(\s*"<name>"`.
- **Long options** via `\{\s*"<name>"\s*,\s*OPT_[A-Z0-9_]+\s*,`.
- **SQL commands** via `\bSQLCOM_<NAME>\b`.
- **Yacc tokens** via `^\s*%token\s+(?:<\w+>\s+)?<NAME>` in `.yy`/`.y` files.
- **InnoDB globals** via `^\s*(?:UNIV_INTERN\s+|extern\s+)?[\w*]+\s+(srv_<…>|innobase_<…>|log_online_<…>)\s*[\(=;]`.
- **Notable macros** (UPPER_SNAKE ≥ 6 chars) and **notable types** (PascalCase ≥ 8 chars) from `symbols.json`.
- **Content feature tags** derived from concrete artifacts, in priority order: sysvars/options, MTR test stems, file-structure signals, InnoDB globals, notable macros/types, then SQL/yacc names as last-resort weak tags. Tags intentionally avoid using the commit subject unless no content tag exists.
- **File-structure signals** from both new and changed paths, with stronger weight for new paths: `mysql-test/` suite/test stems, `plugin/<name>/...`, `sql/<feature-ish-file>`, `storage/innobase/<module>/<file>`, and selected `scripts/`, `client/`, `include/`, `mysys/` paths. Generic infrastructure filenames such as `sql_parse`, `ha_innodb`, `row0sel`, and `lock0lock` are down-filtered so they do not dominate feature tags.

Writes `$WORK_DIR/features-report.md` — per-commit detail plus a "flat catalog" indexed by sysvar/SQLCOM/option name. Also writes `$WORK_DIR/features.json`, including `feature_tags` with tag scores and source artifacts.

### Phase 5 — Combined relatedness (`scripts/relatedness.py`)

For every commit pair, combine the four signals into an edge weight:

```
w(A, B) = log1p(hunk_w) * 3 + file_w * 1.5 + tok_w * 8 + sym_w * 0.5
```

Coefficients chosen empirically against PS 5.6 import-heavy ranges: tokens dominate (strongest semantic signal), then sysvar/file co-occurrence with TF-IDF, then line overlap (log-compressed because some commits touch huge headers), then symbol-level (already pre-weighted internally).

Writes `$WORK_DIR/relatedness-edges.tsv` with `(idx_A, idx_B, w, components)`.

### Phase 5.5 — Inverse-diff replacement/revert candidates (`scripts/replacements.py`)

For each pair `(A, B)` where `A` is earlier than `B`, parse exact added/deleted textual lines from `git show -U0` and compute:

- `deletes_earlier_adds`: lines added by `A` that are deleted by `B`.
- `readds_earlier_deletes`: lines deleted by `A` that are re-added by `B`.
- `score`: sum of those two counts.

Pairs with `score >= $REPLACEMENT_MIN_SCORE` (default `3`) are reported as replacement/revert candidates. The pass then loads the hunk dependency DAG and classifies movability:

- `adjacent`: candidate commits are already adjacent.
- `move-member-up`: the later member has no dependency blockers above the carrier.
- `move-carrier-down`: the carrier has no dependency blockers below it.
- `blocked`: both directions have hunk-DAG blockers.

Writes `$WORK_DIR/replacements.json`, `$WORK_DIR/replacements.tsv`, and `$WORK_DIR/replacement-candidates.md`. These are squash-planning candidates, not automatic squash approvals. Phase 7 also consumes `replacements.json` as an affinity signal for cluster assignment.

### Phase 6 — Seed identification (`scripts/seeds.py`)

If `$SEEDS_FILE` does not exist, identify candidate seeds automatically:

- Any commit that introduces a **new subsystem-anchor file** (a new file not in any sibling commit's diff list, in `sql/`, `storage/innobase/`, `plugin/`, where the file is also referenced as a context by another commit).
- Any commit that introduces ≥ 5 new sysvars, OR ≥ 3 new SQLCOM, OR ≥ 3 new yacc tokens, OR creates ≥ 20 new files.
- Any commit that creates a plugin subtree (≥ 3 new files under `plugin/`).
- Any feature-anchor subject (`Implement`, `Implementation`, `Port`, `Blueprint`, `Add support`, or targeted tuning subjects) with enough code/test footprint. This catches medium-sized feature imports that do not introduce many sysvars or SQL grammar entries. Leading bracketed markers are stripped before this check.
- Any commit whose marker-stripped subject matches `Import\s+<patch_name>\.patch` and where `<patch_name>` is also referenced as a token by ≥ 2 other commits.

For each candidate, derive a short feature name from content first:

- Use the top `features.json[*].feature_tags[*].tag` when present. This avoids labels that are just parsed bug subjects, e.g. `UPDATE/DELETE with LIMIT clause unsafe...` should become a content tag such as `binlog_unsafe_limit` when the commit adds `mysql-test/.../percona_binlog_unsafe_limit`.
- If no content tag exists, use a blueprint/spec slug from subject/body.
- If neither exists, fall back to a sanitized subject.

Writes `$WORK_DIR/seeds.tsv` and `$WORK_DIR/seed-suggestions.md`. **The engineer reviews and edits `seeds.tsv` before phase 7** — adding human-readable names, merging seeds that should be one feature, removing false-positive seeds. The format:

```
feature_name<TAB>seed_idx_1,seed_idx_2,...
```

### Phase 7 — Seeded clustering + report (`scripts/cluster.py`)

Before assignment, combine all available pairwise signals into `$WORK_DIR/combined-edges.tsv`:

```
combined_w(A, B) =
  base_relatedness_w(A, B)
  + min(log1p(replacement_score(A, B)) * $REPLACEMENT_AFFINITY_SCALE,
        $REPLACEMENT_AFFINITY_CAP)
```

`base_relatedness_w` is the Phase 5 hunk/file/token/symbol score. The replacement term is zero when `replacements.json` has no candidate for the pair.

Before satellite assignment, run a conservative seed-feature merge pass. Two seed features merge into one cluster when at least one seed-to-seed pair has:

- `combined_w >= $SEED_MERGE_AFFINITY`
- `replacement_score >= $SEED_MERGE_REPLACEMENT_MIN_SCORE`
- replacement movability other than `blocked`, unless `$SEED_MERGE_REQUIRE_MOVABLE=0`

This lets the clusterer combine features that were originally detected as separate seeds but are clearly replacement/update stages of one feature, while avoiding broad shared-file-only InnoDB merges.

For each non-seed commit, compute affinity to each merged feature as `max(combined_w(commit, seed_member) for seed_member in feature.seeds)`. Assign to the winning feature provided:

- Winner affinity ≥ `$MIN_AFFINITY`, and
- Winner exceeds runner-up by ≥ `$MARGIN`.

Else the commit is **ambiguous** (winner reported but unassigned) or **unassigned** (no affinity met threshold).

Apply a second pass: unassigned commits may join a cluster via their best **already-assigned-member** using the same combined affinity if that affinity meets the threshold and margin (transitive expansion). This catches satellites whose strongest link is to another satellite, not to the seed itself.

Classify satellites:

- **Strong**: affinity ≥ `$STRONG_AFFINITY`
- **Weak**: `$MIN_AFFINITY` ≤ affinity < `$STRONG_AFFINITY`

Writes `$WORK_DIR/cluster-summary.md` with:

1. Methodology block (signal weights, thresholds)
2. **Cluster summary table** — one row per feature, columns: `Feature | Seeds | Strong satellites | Weak satellites | Total`
3. **Merged seed features** — if the seed merge pass joined any seed features, list the joined feature names, seed pair, combined affinity, and replacement signal.
4. **Per-cluster detail** — for each feature, list seed (★) + each satellite with per-commit shortstat, combined affinity for satellites, and the dominant signal description (e.g. "co-def `QPLAN_TMP_DISK`", "31 shared `(file, function)` contexts in btr0*", "inverse-diff score=63").
5. **Inverse-diff replacement/revert candidates** — if `replacements.json` exists, list top replacement candidates with score and DAG movability.
6. **Per-commit feature impact** — for every commit, report:
   - `introduced`: seed feature names plus mined feature-catalog artifacts from `features.json` (sysvars, options, SQLCOMs, yacc tokens, InnoDB globals, new files, notable macros/types).
   - `updated`: cluster feature updated as a strong/weak satellite, with affinity and anchor commit.
   - `removes/replaces`: inverse-diff evidence that this commit removes/replaces a feature from an earlier commit, naming that carrier commit.
   - `replaced by`: reverse view for earlier commits whose added lines are later removed or whose deleted lines are later re-added.
7. **Ambiguous commits table**
8. **Unassigned commits table**
9. **Suggested manual adjustments** — heuristic flags for likely false-positive satellites (very low affinity, single noisy-identifier link)

Also writes `$WORK_DIR/combined-edges.tsv`, `$WORK_DIR/seed-feature-merges.json`, and `$WORK_DIR/commit-feature-impact.json`, the machine-readable form of the per-commit feature impact table.

## Top-level driver

```bash
export BASE_BRANCH=mysql-5.6.26
export TIP_BRANCH=vps-5.6.26-clean
export WORK_DIR=/tmp/ps-feature-cluster-${TIP_BRANCH}
mkdir -p $WORK_DIR

python3 ~/.claude/skills/ps-feature-cluster/scripts/index.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/depgraph.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/symbols.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/features.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/relatedness.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/replacements.py
python3 ~/.claude/skills/ps-feature-cluster/scripts/seeds.py

# Engineer reviews $WORK_DIR/seed-suggestions.md and edits $WORK_DIR/seeds.tsv:
#   - merge auto-detected seeds that are really one feature (e.g. multi-member)
#   - give human-readable feature names
#   - remove false-positive seeds (e.g. a commit that creates many test files but
#     isn't a feature anchor)

python3 ~/.claude/skills/ps-feature-cluster/scripts/cluster.py

# Outputs:
#   $WORK_DIR/features-report.md  — per-commit introduced features catalogue
#   $WORK_DIR/cluster-summary.md  — the deliverable: cluster table + per-cluster detail
#   $WORK_DIR/combined-edges.tsv — base + replacement/revert affinity per pair
#   $WORK_DIR/seed-feature-merges.json — seed features merged before satellite assignment
#   $WORK_DIR/commit-feature-impact.json — introduced/updated/replaced impact per commit
```

## Non-goals

- **No squash, no rewrite, no cherry-pick.** Use `ps-squash-dag` afterwards if you want to materialise the clusters.
- **No per-commit build verification.** This is pure analysis on the existing range.
- **No automatic seed naming for new domains.** The auto-seed heuristic works well for Percona Server's import-heavy history; for other codebases the engineer should provide `$SEEDS_FILE` directly.
- **No mid-range edit detection.** If the range gets squashed/edited during analysis, re-run phase 1 onwards (the indices will shift).

## Differences from related skills

| | `ps-squash-dag` | `ps-feature-cluster` |
| --- | --- | --- |
| Output | New branch with squashed commits | Two markdown reports |
| Modifies branches | yes | **no** |
| Pair detection | tokens + exact subjects only | full relatedness graph |
| Per-commit feature catalog | no | yes (`features-report.md`) |
| Seed-based clustering | no (pair-by-pair) | yes (multi-seed per feature) |
| Hunk-level dep graph | yes (for movability check) | yes (as one of four signals) |
| Symbol-level edges | no | yes (`co_def` / `def_use` / `shared_ctx`) |
| TF-IDF file weighting | no | yes |
| Output rendered to engineer | `pair-report.md` for approval | `cluster-summary.md` as the deliverable |

## When to use

- **Discovering structure** in an unfamiliar Percona Server commit range — what features exist, which commits implement them, which commits are satellites vs anchors.
- **Pre-port planning** — group commits by feature to decide which groups to land first when porting to a newer base (combine with `ps-port-grouped`).
- **Pre-squash planning** — generate cluster definitions to feed into a squash tool (combine with `ps-squash-dag` or its feature variant).
- **Diff-noise diagnosis** — when a commit's subject doesn't match what it actually does (e.g. our run found that "Move libmysqlclient.so" is actually a 14-file InnoDB rebrand), the symbol-level graph surfaces this loudly.
